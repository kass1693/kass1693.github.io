04 / 장애 재현·분석

인증 로그와 실제 송신 상태를 대조했습니다.

5GHz 비콘은 계속 송신됐지만 인증 응답이 나가지 않는 상태였습니다. hostapd 로그와 대역별 송신 통계를 확인하고, ALTX 큐와 PLE 버퍼, WFDMA 송신 링의 상태를 시간순으로 비교했습니다.

측정 대상확인한 내용
2.4GHz 송신EDCCA가 활성화된 상태에서 비콘과 송신 카운트가 증가하지 않았습니다.
ALTX 큐·PLE 버퍼ALTX Q0와 공용 HIF 버퍼 사용량이 함께 증가하다 포화됐습니다. 이때 ALTX Q0의 패킷 수와 HIF 사용량은 모두 0xd5a였습니다.
호스트 송신 링송신 큐가 포화된 상태에서 수 초 간격으로 두 차례 측정했지만, CIDX/DIDX가 변하지 않았습니다.
5GHz 송신인증 응답 처리 로그는 남았지만, 같은 구간의 송신 카운트는 비콘 카운트와 같았습니다.

조건을 바꿔 같은 장애 재현

2.4GHz EDCCA 임계값을 낮춰 송신 차단을 유지했습니다. 약 55분 후 ALTX 큐가 포화됐고, 5GHz 접속 실패도 다시 나타났습니다.

차단 해제 후 복구 확인

ED 측정값이 여전히 최대인 상태에서 EDCCA 차단을 해제하자 큐와 버퍼 사용량이 줄고 통신이 복구됐습니다.

대응 방향. 프레임 만료 처리, 대역별 자원 분리, 송신 큐 보호를 수정 후보로 정리하고 칩셋사에 확인할 항목을 남겼습니다.

키를 요청하고 응답을 해석한 뒤, 성공·실패에 따라 키 상태를 변경합니다.

실패 시 처리

최초 획득에 실패하면 Emergency Key의 사용 가능 여부를 확인하고, 갱신에 실패하면 기존 키를 유지합니다.

송수신 키 선택

송신할 때는 키 테이블에서 사용 가능한 첫 번째 키를 선택합니다. 수신할 때는 패킷의 Key Version과 일치하는 키를 찾습니다.

관리 프로토콜

SNMP · Trap · Holepunch · Syslog에 같은 키 관리 정책과 암호화 처리를 적용했습니다.

03 / 제품 적용

Wi-Fi 6에서 적용한 기능을 Wi-Fi 7으로 확장했습니다.

2025년 9월 첫 현장 적용 이후 해당 기능 관련 필드 문제 접수·대응은 0건이었고, 이후 Wi-Fi 7 제품에도 같은 기능을 적용했습니다.

01 / 장비 측 설계

규격에 맞춰 장비 내부의 키 관리 정책을 설계했습니다.

규격에는 Main Key를 휘발성 저장소에, Emergency Key를 비휘발성 저장소에 보관하도록 정해져 있었습니다. 실패·갱신 시의 기본 동작도 규격을 따랐습니다. 이를 여러 프로세스가 공유하기 위한 파일 구조와 상태 구분 방식은 직접 설계했습니다.

장비 측 구현 범위

  • 키 요청과 응답 해석, 최초 획득·갱신·재시도 및 실패 시 대체 키 사용
  • Main/Emergency Key의 파일 저장 방식과 상태 구분 정책
  • 송신 키 선택과 수신 패킷의 Key Version에 따른 복호화 정책
  • SNMP·Trap·Holepunch·Syslog의 암호화·복호화 연동
  • 설정·부팅·서비스·방화벽·운영 보고 기능과 연동

규격으로 정해진 내용과 직접 설계한 내용

  • Main/Emergency Key의 역할과 기본 동작은 규격에 정의
  • 키 관리 서버는 외부 업체가 개발
  • 장비 내부의 키 파일 구조, 상태 구분 정책과 송수신 시 키 사용 방식은 직접 설계

02 / 키 파일 정책

파일 상태키 준비 상태처리 기준
파일 없음결과 대기키 교환 결과를 기다리는 상태입니다.

03 / 키 선택·실패 처리

송신과 수신의 키 선택

송신

테이블에서 사용 가능한 첫 번째 키

키 획득에 성공하면 첫 번째 Main Key를 사용합니다. 최초 획득에 실패해 저장된 Emergency Key를 키 테이블에 불러온 경우에는 해당 키를 사용합니다.

Key Version 식별자도 패킷에 담아 전송합니다.

수신

패킷의 Key Version과 일치하는 키

현재 송신에 쓰는 키와 무관하게, 수신 패킷의 Key Version에 맞는 키를 찾아 복호화합니다.

수신 시에는 Main Key와 Emergency Key를 별도로 구분하지 않습니다.

01 / 공통 구조

HTTP 요청을 처리하는 공통 프레임워크를 만들었습니다.

공통 HTTP 처리는 Framework에서, 제품 API는 Application에서 담당하도록 나눴습니다. HTTP 라이브러리 연동은 어댑터에서, 실제 장비 접근은 Infra에서 처리합니다.

HTTP ↔ FRAMEWORK ↔ APPLICATION

02 기존 구성 분해
03 새 구성 조립

유지되는 부분바뀌지 않는 구성 요소는 그대로 남습니다.
구조 보기

API 규격을 바꾸면 오른쪽 제품 API가, HTTP 엔진을 바꾸면 왼쪽 엔진과 연결 어댑터가 교체됩니다.

변경 범위를 보여주기 위한 애니메이션입니다. 버튼을 누를 때마다 초기 구성에서 다시 시작합니다. 실제 실행 중에 엔진을 교체하거나 코드를 전부 다시 작성한다는 뜻은 아닙니다.

01 / 서비스 구성

기존 웹서버 대신 독립 REST 서비스를 선택했습니다.

당시 제품에는 REST API 전용 데몬이 없었고, 기존 웹서버를 다른 포트로 실행해 사용하자는 의견도 있었습니다. 여러 AP 제품에 적용할 가능성과 웹 UI·REST API의 목적 차이를 고려해 별도 서비스를 만들기로 했습니다.

기존 웹서버에 종속시키지 않은 이유

  • 탑재할 AP 제품이 정해지지 않았거나, 여러 제품에 적용할 가능성이 있었음
  • 웹 UI와 REST API는 제공하는 기능과 수정이 필요한 이유가 다름
  • 기존 웹서버에 기능을 추가하면 다른 제품에 이식할 때도 그 웹서버에 의존하게 됨
  • 전용 데몬과 공통 프레임워크를 새로 구현하기로 결정

구현 전에 정한 아키텍처

  • CivetWeb/Mongoose 같은 HTTP 라이브러리를 Application과 분리
  • MIB·드라이버·설정 유틸 같은 장비 접근 코드를 Infra로 분리
  • Framework와 Application 역할을 구현 전에 분리
  • Endpoint / Controller / UseCase는 설계 단계부터 포함
